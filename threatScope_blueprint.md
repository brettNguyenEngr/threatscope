# ThreatScope Blueprint: Agile Agentic Cybersecurity Scanner

## 1. Project Overview
This document serves as the master reference guide for building **ThreatScope**, a "Human-in-the-loop" Agentic Cybersecurity Scanner. The system leverages Cloud-Native architectures (Docker), RAG (Retrieval-Augmented Generation), and Agentic Workflows to scan a local network using **Nmap**, while maintaining strict user trust through a **Read-Only Observability** approach. 

To prove the system's efficacy safely, the project utilizes a **Metasploitable 3** Docker container as a controlled, deliberately vulnerable sandbox target.

### The "Trust Gap" Solution & Read-Only Observability
To address concerns about blind, autonomous network scanning, this application operates on a **Glass Box** principle using the Principle of Least Privilege:
* The agent has **Visibility-Only Agency**. It can observe ports and service banners but cannot execute system-level commands, modify configurations, or patch systems.
* **Investigate, Don't Fix:** The agent performs a deep, multi-pass ReAct (Reason + Act) loop to investigate vulnerabilities but stops short of remediation, instead providing an evidence-based "Human Verdict" report.

## 2. Architecture & Components

The application is fully containerized using Docker Compose, divided into distinct zones:

### A. Frontend Container (The UI)
* **Tech Stack:** Streamlit, Python
* **Purpose:** Provides a standalone, easy-to-use desktop-like interface.
* **Responsibilities:** Display network status, show the Agent's reasoning, and render the final vulnerability report.

### B. Backend Container (The Agentic Brain)
* **Tech Stack:** FastAPI, Python, LangChain/Requests
* **Purpose:** Acts as the orchestrator.
* **Responsibilities:**
  * Communicate with the LLM API (e.g., OpenRouter).
  * Manage the **ReAct Agentic Loop** (Observe -> Think -> Retrieve -> Act).
  * Query the RAG database for context.

### C. Database Container(s) (The Memory)
* **PostgreSQL:** Stores scan history and historical risk trends.
* **ChromaDB:** A vector database acting as the RAG Knowledge Base. It dynamically stores CVE descriptions fetched during the scan.

### D. Tools Container (The Hands)
* **Tech Stack:** Kali/Ubuntu base image, `nmap`, Nmap Scripting Engine (NSE)
* **Purpose:** Safely isolates the scanning tools. Uses `vulners.nse` to map open services directly to known CVEs.

### E. Target Sandbox (The Control)
* **Tech Stack:** Metasploitable 3
* **Purpose:** A deliberately vulnerable target isolated on the Docker network to guarantee scan results and prove the tool works without scanning real, sensitive university or home networks.

## 3. Agile Implementation Timeline (Iterations)

Instead of a waterfall approach, ThreatScope is built via rapid prototyping. Each iteration produces a fully functional vertical slice of the application.

### Iteration v0.1: The "Walking Skeleton" (End-to-End Plumbing)
**Goal:** Prove the Docker network, UI, Backend, and DB can communicate. No AI, no real hacking tools.
* **Frontend:** Streamlit has a "Target IP" input and a "Run Scan" button.
* **Backend:** FastAPI receives the IP, waits 3 seconds (simulating work), and returns a hardcoded, fake JSON "Manifest" and "Verdict."
* **Database:** Postgres saves the fake scan result.
* **Deliverable:** You can click a button in the UI, data travels through the FastAPI backend to the Postgres DB, and the UI displays the fake result. 

### Iteration v0.2: The "Blind Scanner" (Tool Integration)
**Goal:** Connect the "Hands" (Nmap) and target environment. Still no AI.
* **Target:** Spin up the `metasploitable` container in the Docker network.
* **Backend:** Replace the 3-second wait with a Python subprocess that runs a basic `nmap -sV <metasploitable_ip>`.
* **Frontend:** The UI now displays the raw XML/JSON Nmap output.
* **Deliverable:** Your app successfully executes a real network scan on the Metasploitable container and surfaces the raw results to the user.

### Iteration v0.3: The "Linear Analyst" (LLM & Vulners)
**Goal:** Introduce the LLM to interpret the data (Lab 9 concept: Judge).
* **Tools:** Upgrade the Nmap command to use `--script vulners` so it returns actual CVE IDs.
* **Backend:** Take the Vulners CVE output and send it to your LLM API (OpenRouter) with a static prompt (e.g., *"Explain these vulnerabilities to a user."*).
* **Frontend:** The UI now displays a "Human-Readable Report" generated by the AI alongside the raw data.
* **Deliverable:** The system translates raw, confusing Nmap/Vulners output into a coherent, single-pass security brief.

### Iteration v0.4: The "Security Agent" (ReAct Loop & RAG)
**Goal:** Implement the multi-pass Agentic Loop and the ChromaDB memory (Lab 8 & Lab 9 full integration).
* **RAG (Lab 8):** When the Vulners script finds a CVE, the backend dynamically fetches the NVD description, stores it in ChromaDB, and the LLM retrieves it for context.
* **ReAct Loop (Lab 9):** Implement the `while` loop logic. (e.g., Agent runs a ping sweep -> observes -> decides to run version scan -> observes -> fetches RAG data -> writes final report).
* **Frontend:** The UI streams the agent's "Thought Process" live before showing the final report.
* **Deliverable:** The app autonomously chains observations and actions together, relying on RAG memory, before finalizing the report.

## 4. Requirements & Dependencies

**System:**
* Docker Desktop installed locally.

**Environment Variables (`.env`):**
* `OPENROUTER_API_KEY` (or other LLM provider)
* `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`
* `CHROMA_PERSIST_DIRECTORY`

**Python Packages (Backend/Frontend):**
* `fastapi`, `uvicorn`, `requests`
* `streamlit`
* `python-nmap`
* `chromadb`, `sentence-transformers`
* `psycopg2-binary`, `sqlalchemy`
